🔬 Fuzzing Engine

Udaya includes a built-in fuzzing engine that systematically tests the node's resilience against malformed and edge-case inputs. The fuzzer generates millions of mutated inputs and validates that the node handles all scenarios gracefully.

Fuzzing Coverage Areas
  • Block Header Deserialization — Mutations of timestamp, nonce, merkle root, bits, version fields with boundary values, zero values, maximum values, and random byte sequences
  • Transaction Deserialization — Mutations of inputs, outputs, scripts, witness data with malformed lengths, invalid opcodes, oversized scripts, and corrupted signatures
  • Serialization Round-Trips — Encode-decode-encode consistency checks ensure that serialization is always reversible and deterministic
  • Mempool Operations — Duplicate transactions, conflicting spends, zero-fee transactions, oversized transactions, and transactions with invalid locktimes
  • Consensus Rules — Difficulty target violations, invalid proof-of-work, signature verification edge cases, coinbase maturity violations, and block version enforcement
  • Network Messages — Malformed inv messages, oversized getdata requests, invalid addr payloads, corrupted version handshakes

⚔️ Adversarial Attack Simulations

Udaya includes a comprehensive simulation engine that tests the network's resilience against real-world attack scenarios. Each simulation models the attack lifecycle and measures the node's ability to detect, resist, and recover.

🔄 Double Spend Attacks

Simulates race attacks, Finney attacks (pre-mined), and Vector76 attacks (multiple conflicting transactions). The mempool consensus rules correctly reject double spends at the transaction validation layer.

100% Detection

⛏️ Selfish Mining

Simulates block withholding strategies where a miner privately mines blocks and selectively reveals them. Udaya's timestamp analysis and reorg limits prevent profitable selfish mining beyond 6 blocks.

Réorg Limit: 6 Blocks

🌑 Eclipse Attack

Simulates connection isolation by flooding the node with malicious peers. Udaya's address manager rotates connections and maintains a ban list. Maximum 125 connections with 8 outbound slots reserved for honest peers.

125 Max Connections

👥 Sybil Attack

Simulates identity flooding where an attacker creates thousands of fake nodes. The node limits connection attempts per IP range and employs address bucket randomization to maintain network diversity.

Bucket Randomization

📬 Mempool Spam

Simulates transaction flooding with dust outputs, zero-fee transactions, and high volumes. Per-peer rate limiting (100 tx/peer/sec) and mempool size limits with fee-based eviction prevent resource exhaustion.

100 tx/s Limit

⛓️ Chain Reorganization

Simulates deep chain reorg attempts by mining blocks at fork heights. Udaya enforces a maximum 6-block reorg depth. Any reorg attempt beyond 6 blocks is rejected at the consensus level.

6-Block Reorg Limit

🔀 Chain Split Detection

Udaya implements real-time chain split monitoring to detect and alert on competing blocks at the same height. This is critical for maintaining network consensus and preventing confusion during potential fork events.

Detection Mechanism

  • Real-Time Monitoring — The node continuously observes the block header stream and logs any instance where two blocks share the same height
  • Automatic Alerting — Chain split events trigger immediate alerts through the Prometheus metrics system and Grafana dashboards
  • Cross-Node Verification — Orchestration scripts provide automated comparison of chain state across multiple nodes to detect consensus divergence
  • Fork Analysis — When a split is detected, the system records the block hashes, timestamps, and connected peers involved in each fork branch
  • Recovery Monitoring — After a split, the system tracks which fork ultimately becomes the dominant chain and measures the time to resolution

🌊 Flood Protection

Udaya implements multi-layered flood protection to prevent resource exhaustion and denial-of-service attacks at the network level.

Rate Limiting Implementation

Per-peer rate limiting uses a sliding window algorithm that tracks the number of transactions received from each peer within a 1-second window. Peers that exceed the limit receive a warning; repeated violations increment the ban score. Once a peer's ban score reaches 100, they are automatically banned for 24 hours. Ban scores decay by 1 point per hour of good behavior.

🛡️ Security Principles

🔍 Defense in Depth

No single layer is trusted to provide complete security. Every component validates inputs from upstream layers, ensuring that a failure in one layer does not compromise the whole system.

🧪 Test Everything

All security-critical code paths are covered by fuzzing, unit tests, and integration tests. The fuzzing engine runs continuously in CI, with every code change subjected to millions of randomized inputs.

🚨 Fail Safe

When the node encounters unexpected or malformed input, it defaults to the safest behavior — reject the input, log the event, and continue operating without crashing or compromising state.

📢 Transparent Reporting

All security findings — including their severity, impact, and remediation — are published transparently on the trust portal. There are no hidden vulnerabilities.

📢 Responsible Disclosure

Udaya maintains a responsible disclosure program for security researchers. If you discover a vulnerability in the Udaya codebase, please report it through our bug bounty program.

  • Email: security@Udaya.org
  • PGP Key: Available on the trust portal for encrypted communication
  • Response Time: Initial response within 24 hours, resolution within 7 days for critical issues
  • Bounty: Rewards range from 100 to 10,000 UDYA depending on severity
  • Safe Harbor: Researchers acting in good faith will not face legal action
